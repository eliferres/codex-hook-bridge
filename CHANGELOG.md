# Changelog

All notable changes to this project are documented in this file, in the format of [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [0.1.0] - 2026-10-02

### Added

- `codex-hook-bridge hook`, run by Codex as a hook, which runs your Claude Code hooks over each Codex call and returns their verdicts in the shape Codex expects for that event; a `continue: false` from a `Stop` or `SubagentStop` hook passes through as itself.
- Codex shell calls reach `Bash` hooks, and every file a shell command writes also reaches `Write` hooks, resolved in the folder any `cd` in the command moved to, including writes behind `bash -lc`, `eval`, `timeout`, `stdbuf`, keywords such as `do` and `!`, subshells, `$( ... )`, `cp -t` and clustered options such as `curl -sSo` and `wget -qO`; each path `git restore` puts back reaches both `Write` and `Edit` hooks. The folder `tar -C` or `unzip -d` extracts into is reported both with and without a trailing slash, and a written path given with a trailing slash keeps it. A `local_shell` command given as `action.command` is read, and resolved in its `action.working_directory`, and an argv command is joined with shell quoting.
- An `apply_patch` reaches your file hooks file by file, read the way Codex reads it (indented headers, lines split on newline only): `Write` for an added file, one `Edit` per hunk of an updated one, `rm` and `mv` as `Bash` for deletes and renames. Every patch inside a shell command is read, in the folder any `cd` before it moved to; a `cd` inside quotes or in a subshell that has closed does not count, and one into a folder that does not exist, followed by `;` or a newline, counts both the old and the new folder, for shell writes too. A `..` after a symlinked folder resolves to where the file really lands. A patch whose body is under a field the bridge does not read passes through as `apply_patch`.
- Every matching hook, a `*` or empty matcher included, runs once on each payload a Codex call becomes, all in parallel within one time budget.
- Code-mode scripts, image views, web searches, user questions, subagent spawns, subagent messages and MCP tools are translated to their Claude Code counterparts.
- Hooks are read from the user, project and local Claude Code settings files, merged the way Claude Code merges them, with `--settings` to name files instead and `--project-dir` to set the project folder hooks see as `CLAUDE_PROJECT_DIR`. In hook mode a settings file that exists but is malformed is skipped on its own and named on stderr, and every other file's hooks still run; `parity` treats it as an error.
- Hooks that read `transcript_path` get a Claude Code shaped copy of the Codex session log; copies the bridge wrote are pruned after 30 days unwritten, and nothing else in the folder is touched.
- Shell commands are read in one pass, in time proportional to their length; a command over 1,000,000 characters, a chain of `cd`s past a 4,096-character path, or `bash -c` and `eval` nested more than 16 deep is refused with a plain reason when any hook is set for the event, rather than let through unread.
- In hook mode the bridge's own problems (a bad option, a `--settings` file that does not exist, an internal error) are one line on stderr with exit 1, so they never read to Codex as a refusal; a hook that cannot start, and a matcher Python's `re` cannot evaluate, are named on stderr.
- `codex-hook-bridge translate` prints the Claude Code payloads a Codex payload becomes, without running anything.
- `codex-hook-bridge parity` lists every hook route with whether Codex can reach it and why not, and exits 1 on any route nobody accounted for or whose `timeout` is longer than the bridge's budget (`--budget`, as for `hook`); `--accept` takes a file of known exceptions, `--json` prints the report as JSON, and the report states that managed-policy and plugin hooks are not read.
